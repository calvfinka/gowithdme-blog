Building GoWithDME Alone: Why I Chose 4 Services Instead of One Big Server

    There is a question I receive quite often: "How big is the team behind GoWithDME? Where is the server located?"

    The answer might surprise some people: GoWithDME is built and managed by one person. Me.

    Not because I want to work alone. But because from the beginning, I wanted to build something lean, fast, and sustainable without having to carry a large operational cost. I did not want to be trapped in server complexity that needs to be maintained every day. I wanted to focus on the one thing that matters most: the experience of users who come to find concerts, festivals, or a companion to travel with.

    From that thinking, the architecture that GoWithDME uses today was born. Not one big server doing everything, but four services, each focused on its own expertise.

    1. Rumahweb: The Foundation of Identity

    It all starts with a name. The domain gowithdme.com is registered and managed through Rumahweb.

    Its role might look simple, but it is the foundation of identity. It ensures that this name is legally registered, can be accessed from all over the world, and its direction can be managed as needed. Without proper domain management, no matter how great the website is, people will not be able to find it.

    I chose to separate domain management from other services so that if I ever need to move infrastructure in the future, the identity of GoWithDME remains safe and is not dependent on a single provider.

    2. Cloudflare: The Layer of Security and Speed

    After the domain name is secured, the next step is to ensure everyone who accesses it gets a fast and safe experience. This is where Cloudflare comes in.

    Every visitor who opens GoWithDME will go through Cloudflare first. Cloudflare works in two main functions.

    First, as a security layer. It filters suspicious traffic, bots, and attack attempts before that traffic reaches the website. This is important, because a website that is open to the public is always a target.

    Second, as a content delivery network, or CDN. Cloudflare stores copies of GoWithDME content on servers spread across many countries. That means, when someone in Bandung opens GoWithDME, they do not need to fetch data from a server far away in the United States. They will be served by the nearest server. The result is faster load time, and a more comfortable experience.

    For me, this is a rational decision. I do not need to build my own servers in many countries just to make a website feel fast.

    3. GitHub: Where The Website Is Built

    If Rumahweb is the identity and Cloudflare is the guard, then GitHub is where the website itself is built and stored.

    All the pages you see on GoWithDME, from the homepage, event pages, to the About page, are stored as files on GitHub. Every change I make, for example updating a description or fixing the layout, will automatically be published as the newest version seen by visitors.

    This approach makes the development process transparent and structured. I can track every change, revert to a previous version if something goes wrong, and develop new features without disrupting the live website.

    This is a common working method used by many modern digital products, because it separates the building process from the presentation process.

    4. Supabase: Where Living Data Is Stored

    Then, what about data that is always changing? Like the latest event data, conversations with Dea AI, or invitations to find travel companions?

    That kind of data cannot be stored as static files. It needs a living place, one that can be updated in real-time and securely. For that, GoWithDME uses Supabase.

    Supabase acts as the database. When you ask Dea AI about events in your city, the answer is not taken from a static file, but from data managed in Supabase. When a new event is added, that data is also stored there.

    This separation keeps GoWithDME lightweight on the front-end, but still dynamic on the back-end.

    Why Not Just Use One Service?

    It is a fair question. Wouldn't it be easier if one service did everything?

    My experience says otherwise. When one system is forced to do everything, it tends to become slow, expensive, and difficult to fix when a problem occurs. If one part fails, the whole system stops.

    By separating roles, each service only needs to do one thing very well. If I want to improve security, I focus on Cloudflare. If I want to add a feature, I focus on GitHub and Supabase. Nothing interferes with each other.

    This is the principle I have held since the beginning: build simple, but build it right.

    Closing: Small Does Not Mean Simple

    GoWithDME might look simple from the outside. A website to find events and friends to watch with. But behind that simplicity, there are technical decisions made consciously so that this product can run fast, safely, and sustainably.

    I believe a good product does not always have to be built by a big team or with expensive infrastructure. Sometimes, it only needs clarity about what you want to build, and the courage to choose the right tools.

    And for me, these four services are the right tools for this stage of GoWithDME.
